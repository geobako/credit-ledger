# 0007: AWS with ECS Fargate, RDS Postgres Multi-AZ and CloudFront

**Status:** accepted

## Context

The services are two small containers and a Postgres database with strict durability needs.
The team should spend time on the money, not on running Kubernetes.

## Decision

- **Compute:** ECS Fargate (ARM64) in private subnets across 3 AZs. Rolling deploys with the
  deployment circuit breaker (automatic rollback), autoscaling on CPU, read-only root
  filesystems, no ECS Exec in production.
- **Database:** RDS Postgres 17 Multi-AZ:
  - customer-managed KMS key, TLS enforced (`verify-full` against the RDS CA bundle baked into
    the image);
  - 35-day point-in-time recovery, deletion protection;
  - Performance Insights, lock-wait logging.
- **Edge:** CloudFront serves the SPA from a private S3 bucket and proxies `/api/*` to the API
  ALB, so the browser sees one origin. WAF covers managed rules, rate limits, and blocking
  the sandbox and internal network paths. The API ALB accepts only CloudFront (prefix-list
  security group and a secret origin header) and only `/v1/*`.
- **Card network:** a separate ALB with **mutual TLS** (trust store with the network's CA) and
  a source CIDR allow-list. The gateway reaches the API privately via ECS Service Connect.
- **Secrets** are generated by Terraform into Secrets Manager (CMK) and injected at task start.
- **Migrations** run as a one-off ECS task before each API deploy (forward-only, advisory
  lock), never at API boot.
- **ORM:** Drizzle for typed queries and generated migrations, with hand-written SQL migrations
  for triggers and constraints the ORM can't express.

## Consequences

- No cluster to operate; per-task isolation; scaling in seconds.
- Multi-AZ failover gives an RPO of 0 and an RTO of about 1–2 minutes for the database; PITR
  covers operator error.
- Terraform state contains generated secrets, so the state bucket must be encrypted,
  versioned and tightly scoped (documented in DEPLOYMENT.md). Moving to RDS IAM auth or
  managed rotation removes the database password from state.
- Single region. Multi-region active/passive (cross-region replica + promoted standby) is the
  next step if the business needs regional disaster tolerance.

## Alternatives considered

- **EKS.** It is more flexible, but the operational cost isn't justified for two services.
- **Lambda.** Cold starts and per-invocation connection management are a poor fit for a
  latency-bound, connection-pooled, lock-heavy workload.
- **Aurora Postgres.** It is a good option (faster failover, storage scaling). Plain RDS was
  chosen for cost and simplicity at this size; switching is mostly a Terraform change.
